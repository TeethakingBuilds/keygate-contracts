How it works

Three questions, three layers.

Every guarded call passes through each layer in order. Any one of them can say no, and none of them defaults to yes.

keygate-contracts

Four contracts, each with one job.

Kept separate on purpose: an incident response is one deny rule, not a bulk revocation, and deleting the rule restores exactly the state before it.

keygate-core

The capability registry. Issue, renew, revoke and check time-bound grants, with a two-step admin handover and a freeze switch.

registryttl grantspause

keygate-policy

Allow and deny rules per resource and action, in front of a registry. Deny takes an action out of service without touching hundreds of grants.

allow / denydefault effect

keygate-circuit-breaker

Rolling-window budgets that latch closed on a breach and stay closed until an explicit reset. One exploit cannot keep draining in small steps.

rolling windowlatching

keygate-multisig

m-of-n administration. Relays any encoded call once quorum approves, so the registry's admin key is never held by one person.

quorumcall relayowner rotation
Design

Built around how Soroban actually behaves.

Every rule below was verified against the real Soroban host in CI, not just the mocked one.

  • A breach is a value, not an error. A failed call loses its own writes, so the breaker reports Outcome::Breached and keeps the latch.
  • No self-re-entry. A contract cannot call itself, so owner rotation is applied inside the multisig's execute.
  • Lazy windows, lazy expiry. No cron job: windows roll forward on first use, so an idle resource costs nothing.
01 — fail closed

Missing means no.

An unconfigured resource, a missing grant or a paused registry rejects. The server mirrors this: if it can't prove yes, it answers no.

02 — latch

Tripping is sticky.

Time passing and raising the limit do not reopen a tripped breaker. Only an admin reset does.

03 — no single key

Admin through quorum.

Route every admin action through the multisig, so freezing issuance or repointing a policy takes m signatures.

The stack

Contracts, server and SDK.

Contracts hold capabilities on-chain. The server mirrors them from contract events and answers queries. The client builds the calls and checks server decisions before trusting them.
